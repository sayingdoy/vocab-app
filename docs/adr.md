## ADR-0001 — 记忆曲线用固定阶梯，题型难度随阶段上升

- 状态：已采纳
- 日期：2026-09-11
- 决策者：Jason + Hermes

### 背景

需要"定期背单词"能力，且要求利用记忆曲线，并具备考试功能。

### 决策

**1. 间隔重复用固定阶梯，不用完整 SM-2**

阶梯（天）：`1, 2, 4, 7, 15, 30, 60, 120`

- 答对 → `stage + 1`，下次 = 今天 + `LADDER[min(stage, 7)]`
- 答错 → `stage = max(0, stage - 2)`，下次 = 明天，`state = lapsed`
- `stage = 7` → `mastered`

**2. 题型难度随 `stage` 上升**

| stage | 题型 | 线索来源 |
|-------|------|---------|
| 0–1 | A 英→中 | 词 + 音标 |
| 2–4 | B 金句填空 | 中文金句 |
| 5–7 | C 画面猜词 | 原始画面 |

**3. 题目素材取自 ljg-word 的产出，不用词典释义**

考 `serendipity` 不问"意思是什么"，而问"三位王子在旅途中捡起一朵他们从未寻找的花 ——
哪个词？"。金句题给中文「机缘只眷顾那些迷路到肯抬头看的人」让填英文词。

**4.「复习」与「考试」分开**

复习 = 即时反馈；考试 = 集中检验 + retrieval practice。两者都写入同一套复习历史字段。

**5. 逻辑全部落在确定性代码里**

`review.py` 只做计算和文件读写；agent 只做判断性工作（解词、批改自由文本答案、
决定题目呈现顺序）。符合 Karpathy 规则 5。

### 理由

- **可解释**：阶梯一眼能看懂，用户可以自己判断"这词还卡着"是不是设置问题。
  完整 SM-2 的 ease factor 是隐变量，出问题难排查。
- **零依赖**：纯标准库，符合 AGENTS.md §6。
- **难度跟随熟练度**：这是"利用记忆曲线"能落到题目上的唯一实在方式 ——
  同一个词，越熟给的线索越少，逼出主动回忆（retrieval practice）。
  一直给词典释义的复习是识别（recognition），不是回忆（recall），记得浅。
- **考试 ≠ 复习**：retrieval practice 的强化效果主要来自"费力地想"和"事后知道对错"，
  即时反馈会削弱这个张力。

### 被否决的方案

| 方案 | 否决理由 |
|------|---------|
| 完整 SM-2（含 ease factor） | 隐变量多、不可解释，MVP 阶段收益低 |
| 固定每天 N 个词，不看掌握度 | 没有记忆曲线，卡的词永远卡着 |
| 只用"英→中"一种题型 | 识别型复习，记忆强度低 |
| 用 Anki 现成方案 | 用户要求交付物独立可控、可被 agent 分析 |
| 词库放 Obsidian vault | 用户要求交付物独立成文件夹，可整体搬走 |

### 后果

- 词条 frontmatter 是唯一事实来源，`grade` 独占写入 `stage/state/due/reviews/correct/wrong`。
- 若将来要引入 SM-2，只需改 `LADDER` 与升降级函数，数据契约不变。

## ADR-0002 — 交付物根目录即 Obsidian vault（「训练台」）

- 状态：已采纳
- 日期：2026-09-12
- 决策者：Jason + Hermes

### 背景

需求从"本地脚本 + 交付成果文件夹"扩展到"手机上能看词条、能做题、能和 agent 交互"。
候选承载方式：微信聊天窗口 / 静态网页挂 ECS / 独立 Web App / 自建同步的 Obsidian vault。

已核实的事实：

- 用户手机与电脑之间**已有 Obsidian 同步**（LiveSync + 自建 CouchDB on ECS）
- 微信通道虽已连通，但**主动推送会被 iLink 拒绝**（返回 errcode -2），
  机器人只能在用户刚发过消息的会话窗口内响应 —— 不适合"定时出卷/交卷即批改"
- Obsidian 手机端是原生读写环境，可离线阅读，LiveSync 会把改动带回 PC

### 决策

**把交付物根目录本身作为 Obsidian vault，角色定名为「训练台」。**

- vault 根 = `D:\Projects\vocab-app\交付成果`
- 一个文件夹两种身份：既是"可整体搬走的交付成果"，也是"手机上可直接读写的 vault"
- **不复制、不建软链、不挪位置** —— 两者是同一份文件
- 只承载**训练闭环产生的结构化内容**：词库、练习与成绩、统计
- **明确排除**：学习材料、阅读笔记、语法笔记等非闭环内容（要放就另开 vault）

### 理由

- **两个候选角色（"视图" vs "工作台"）被合并**：根目录重合后，脚本读写的目录
  和手机上看到的 vault 是同一个，"谁是数据源"这个争论自动消失。
- **保住了既有的硬约束**：用户已定"交付成果独立、可整体搬走"（ADR-0001 否决项之一）。
  该约束不被牺牲，反而因为 vault 身份而获得手机端读写能力。
- **零额外基础设施**：不需要新建存储、不需要部署服务、不需要 App。
- **边界清晰才可能自动化**：扫描、结算、出题都依赖"这里只有闭环内容"这个前提。

### 被否决的方案

| 方案 | 否决理由 |
|------|---------|
| 微信聊天窗口作为主界面 | 主动推送被 iLink 拒绝（errcode -2，实测 3 次失败）；只能"被动应答"，无法支撑定时出卷与自动结算 |
| 静态网页挂 ECS | 回写词库的闭环别扭（答题结果留在浏览器 localStorage，回 PC 需额外通道） |
| 独立 Web App 挂 ECS | 开发与维护成本最高，且 ECS 2C2G 内存余量不足（Hindsight 已占 ~510Mi） |
| Obsidian 手机版 + 把词库**复制**进现有 vault | 产生两份数据，双写冲突；且污染主 vault |
| Obsidian 手机版 + 在现有 vault 里**建软链**指向交付成果 | 交付成果虽然仍在原地，但英语内容混进主 vault；且依赖 LiveSync 是否穿透 junction，不确定 |
| 新建**独立** vault（不与交付物根目录重合） | 需要新建 CouchDB 库 + 两端重装配置，多一层成本；且"数据源在哪"重新变成待解问题 |

### 后果

- 交付物目录里会多一个 `.obsidian/` 配置目录（Obsidian vault 身份的必要副产品）。
  这不破坏"纯 Markdown、可搬走"的约束 —— 删掉 `.obsidian/` 仍是干净的文件集。
- 手机端同步依赖用户既有的 LiveSync 通道；新 vault 是否需要新 CouchDB 库、
  以及同步是否为自动模式，仍需核实（见「待确认」）。
- 由于 vault 只承载闭环内容，**Obsidian Spaced Repetition 插件不得装入此 vault** ——
  否则会与 `review.py` 争夺 `stage`/`due` 的写入权。SR 插件继续管用户其余笔记。
- 术语「训练台」记录于 `CONTEXT.md`。

### 待核实

1. 用户现有 LiveSync 的 CouchDB admin 口令（连接信息在插件配置中被 E2EE 加密，无法从磁盘读取）
2. 现有同步是否为自动触发（插件配置里 `liveSync` / `periodicReplication` / `syncOnStart`
   均为 `false`，与"手机电脑实时同步"的用户认知不一致）

## ADR-0003 — 模型调用边界：确定性优先，模型只用在"生成"环节

- 状态：已采纳
- 日期：2026-09-12
- 决策者：Jason + Hermes

### 背景

Jason 提出："如果调用 API 成本高，我倾向于尽可能使用 AI chat 的能力。"
需要先量化成本，再决定架构该往哪边偏。

### 已核实数据

- 当前走 **SCNet Token Plan**（包月 ¥30/月，Credits 抵扣，额度用尽即调用失败、不结转）
- 过去 30 天真实用量（`hermes insights`）：27 会话 / 3,684 消息 / 1,779 次工具调用 /
  输入 **20.69M** + 输出 **1.82M** tokens
- 会话实际模型：`deepseek-v4.1-flash`，单价 **命中 0.02 / 未命中 1 / 输出 4**（元/百万），**高峰 ×2**
- 按上述单价折算 30 天用量：**¥7.67（全命中·闲时）～ ¥55.90（全未命中·高峰）/月**
- SCNet 额度：已用 **21,674 credits = 36%** → 月额度 ≈ **60,204 credits**（剩余 ≈ 38,531）

### 决策

**成本不构成约束。架构按"确定性优先"设计，不为省钱牺牲结构。**
模型调用边界如下：

| 环节 | 调模型 | 说明 |
|------|:--:|------|
| 解词（查词） | ✅ | **唯一**需要模型的日常环节 |
| 出卷 / 判定 / 结算回写 / 统计 | ❌ | 纯标准库代码 |
| 结算触发器 | ❌ | cron `--no-agent`，或 Windows 任务计划 |
| 设计 / 异常处理 / 解析非结构化输入 | ✅ | agent 按需出场 |

### 理由

1. **量级极小**：100 词/月 ≈ ¥0.48–1.12（列表价），或 ≈ 200 credits = 月额度的 **0.33%**；
   即使 20 词/天（600 词/月）也只占 **2.0%**
2. **可复现**：判定权归代码后，记分依据可复现 —— 这是记忆曲线可信度的基础
3. **可靠性**：模型调用会因网络/额度波动失败，SCNet 文档明说"额度用尽后调用失败"。
   批改不可依赖模型，否则会出现"交了卷没人改"
4. **真成本是人的时间**：手工搬运 2 分钟/次 × 5 词/天 ≈ 一年 **60 小时**。
   为省 ¥2/月 花 60 小时，账是亏的

### 被否决的方案

| 方案 | 否决理由 |
|------|---------|
| 为省钱把批改交给模型 | 判定必须可复现；且省不到钱（批改本就 ¥0） |
| 用 AI chat 当日常操作口（每次手工搬运） | 省 ¥2/月 花 60 小时，亏 |
| 全流程都在 Hermes 长会话里做 | 纯计算环节交给脚本更快、更稳、更便宜 |

### 后果

- 题型全部改为填词形式（见 `CONTEXT.md` 的题型表与「判定」条）
- 解词若批量执行，**排在闲时窗口**（高峰价翻倍）
- **AI chat 的定位是"批量生产器"**：攒 10–20 个词一次问完 → 分享链接 → 脚本自动抓取入库。
  该链路已验证：DeepSeek 分享对话一次抓取 52 组问答全自动入库
- 长会话上下文的成本主要看**缓存命中率**；Hermes 自估 ¥4/月 低于列表价最优档 ¥7.67，
  说明命中率高、或 SCNet Credits 折算比列表价更低、或估算偏乐观（19 个 session 无定价数据）。
  **以 SCNet 控制台为准**

### 待核实

- SCNet 的 Credits ↔ tokens 换算表（0.33% 这个估算建立在 1 credit ≈ 1000 tokens 的假设上）
- 36% 的消耗是否对应当前订阅月周期（决定额度是否临近上限）

## ADR-0004 — 出卷与结算的触发机制

- 状态：已采纳
- 日期：2026-09-12
- 决策者：Jason + Hermes

### 背景

练习笔记的形态定了（见 `CONTEXT.md`），接下来要定"谁在什么时候动它"。
两个动作的节奏性质不同：**结算**由"用户什么时候答完"驱动，**出卷**由日历驱动。

### 决策

**两个 Hermes cron 任务，都用 `--no-agent`（完全不经过 LLM，零 token）。**

| 任务 | 计划 | 脚本 | 节奏 |
|------|------|------|------|
| `vocab-结算扫描` | `*/10 * * * *` | `~/.hermes/scripts/vocab-settle.py` | 每 10 分钟 |
| `vocab-每日出卷` | `0 7 * * *` | `~/.hermes/scripts/vocab-practice.py` | 每天 07:00 |

- 交付目标：`--deliver local`（练习笔记经 Obsidian 同步到达用户，不走聊天推送）
- 包装脚本放 `~/.hermes/scripts/`（Hermes 的硬要求），**只做转发**，真逻辑仍在 `src/`
- 结算包装做**降噪**：只在"真的结算了"时输出，否则静默 —— 否则每 10 分钟刷一条运行记录

### 理由

- `--no-agent` 的语义经查证为 "Skip the LLM entirely — run --script on schedule and deliver
  its stdout directly"，是本设计"确定性优先"（ADR-0003）的直接落地
- **拆成两个 job**：混在一个 job 里会出现"连答两轮立刻又收到新卷"，节奏失控
- **选 Hermes cron 而非 Windows 任务计划**：`hermes cron list / runs / history` 可看状态与失败，
  运维面更薄；两者硬约束相同（PC 需开机）

### 被否决的方案

| 方案 | 否决理由 |
|------|---------|
| Windows 任务计划程序 | 状态/失败查询要开任务计划界面，运维面更重 |
| Hermes cron 带 agent（默认模式） | 每 10 分钟一次模型调用，纯浪费；且引入模型失败风险 |
| 单 job 同时做出卷与结算 | 会导致连答时连续出新卷 |
| 手动触发（每次让用户说一句） | 依赖用户在场，且违背"交卷即批改"的体验目标 |
| 出卷也排在结算之后立即执行 | 同上，节奏由日历而非答题速度决定更稳 |

### 后果

- PC 必须开机，这是本设计的硬约束（两个 job 都在本机跑）
- 交卷到批改之间存在最多 10 分钟延迟
- 若将来要在手机上收到"已批改"的推送，需另配可用通道（微信主动推送受 iLink 限制，见 ADR-0002）

### 验证

端到端已在一次性账户 `_selftest` 上跑通 15 项检查：交卷判据（全空跳过 / 部分作答跳过 /
全部作答结算）、判定（写对 · 写错 · 显式「不会」· 拼写错误均判错）、阶梯回写
（对 `0→1` 且 due = 今天+2；错 `0→0` 下限保护 且 due = 明天）、成绩单追加到同一份笔记、
`status` 翻为「已批改」、重复扫描不重复结算。

## ADR-0005 — 线索随阶段渐隐（题型线索重构）

- 状态：已采纳
- 日期：2026-09-12
- 决策者：Jason + Hermes

### 背景

Jason 要求："出题的时候也带着单词意象帮助我记忆。"

但原设计（ADR-0001）里"原始画面 / 意象"是 **C 型题（stage 5–7）的专属线索**，
位于难度阶梯的最高一档。若所有题都带意象，C 型失去专属线索，阶梯塌陷。

### 决策

**线索随阶段递减（fading cues），而不是全程给足：**

| stage | 题型 | 线索（题面） |
|:-----:|------|------------|
| 0–1 | A 义→词 | 中文义 **+ 意象**（双线索） |
| 2–4 | B 句→词 | 中文金句 |
| 5–7 | C 画→词 | 原始画面（撤掉中文义） |

### 理由

1. **满足诉求且用在对的位置**：新词第一次考（stage 0）就给意象 —— 那正是最需要记忆锚的
   时刻（首次编码）。等熟练了再给锚，反而是多余的提示。
2. **保住阶梯**：线索只减不增，越熟越难。
3. **符合记忆科学**：编码阶段给丰富线索、提取阶段减少线索（scaffolding / fading cues）。
4. **C 型反而更纯**：撤掉中文义后只剩画面，比原来"画面是唯一线索"更彻底。

### 被否决的方案

| 方案 | 否决理由 |
|------|---------|
| 所有题都带意象 | C 型失去专属线索，难度阶梯塌陷 |
| 意象放在"提示"区、答不出再看 | Obsidian 编辑模式下作答，笔记里一切可见，藏不住 |
| 只在成绩单里给意象 | 事后才给锚，对"当场想起来"没有帮助 |

### 后果

- `review.py` 的 `clue_for()` 改为按阶段输出多行线索
- `CONTEXT.md` 题型表同步更新
- **ADR-0001 的题型线索列由本 ADR 修正**（ADR-0001 其余内容不变，作为历史决策保留）

## ADR-0006 — 交卷规则：答了就判，不再整份跳过

- 状态：已采纳（补记：2026-09-21 实施当时未记，本条为事后追记）
- 日期：2026-09-21
- 决策者：Jason + Hermes

### 背景

旧规则要求"所有题 `答：` 后都有内容"才结算。实际使用中出现：一份卷子答了 7 题、
留 3 题空白 → 整份不判 → 7 题的分数永远进不了系统 → 词的回池不前进 →
次日出卷抽到同一批词，用户看到的是"题目没变化但也没分数"。

### 决策

- **答了就判**：结算器逐题判定，空白题留待下次扫描；已判题号记在密钥文件
  `#judged=` 行 + 成绩单，取并集，幂等可重扫。
- 全部题判完才把 status 翻成「已批改」，否则「部分批改」。
- `\s*` 一律换成 `[ \t]*`：`\s` 跨行，会把下一行题面/说明误当成作答内容
  （2026-09-21 实测：空白题会被凭空判错、`list` 的已答数虚报）。

### 后果

- `settle.py` 重写判定循环；`practice.py list` 计数修正。

## ADR-0007 — 出卷门控：有未作答旧卷就不出新卷

- 状态：已采纳
- 日期：2026-09-21
- 决策者：Jason

### 背景

Jason 原话："不补了，我不想浪费时间反复填写同样的卷纸。以后如果今天的题没有作答，
后续不需要继续出题。"

ADR-0006 之后仍残留一个自动行为：`cmd_new` 在出卷前把"0 作答"的旧笔记悄悄作废
（移到 `.voided/`）再出新卷。问题：用户隔了几天回来，看到的是一堆没答过的卷子
被无声消失、又被同一批词的新卷替换——既浪费了原来的卷面，也没有传达任何信息。

### 决策

- **门控**：出卷前若存在"早于今天且一题都没答"的笔记 → 不出新卷，打印清单并给出出路。
- 未作答的笔记**留在原位**，等两选一：补答（同步回来即结算）或显式 `practice.py void`
  （作废回池）。系统不替用户决定。
- `void` 从自动行为降级为显式子命令。`--force` 保留紧急绕过。

### 被否决的方案

| 方案 | 否决理由 |
|------|---------|
| 维持自动作废重出 | 用户明确反对"反复填同样的卷"；无声删除违背可审计原则 |

### 后果

- 明起 07:00 cron 出卷：若旧卷未答，cron 输出"不出卷"即止，零副作用。

## ADR-0009 — 出卷取词：新词保底配额

- 状态：已被 ADR-0010 取代（「保底」方向被证伪；取词规则改为「新词填空 + 卷长自适应」）
- 日期：2026-10-02
- 决策者：Jason + Hermes

### 背景

`cmd_new` 的取词排序是：

```python
rng.shuffle(words)
words.sort(key=lambda w: (str(w.get("state") or "new") == "new", R.as_date(w.get("due"))))
words = words[: a.n]
```

`state == "new"` 是**布尔键** → 所有新词排在所有非新词之后。原代码注释假定"非新词一旦被判分 due 会前进、
名额自然让给新词"，但该假设**只在答对时成立**：答错 → stage-2、due=明天，错词每天回池，
只要非新词数 ≥ n 就**永久占满**名额。

实测（2026-10-02，账户 jason，词库 49 词）：

- 11 份已出练习卷、共 110 个槽位，只用到 **28 个不同的词**；**21 个新词从未出过卷**。
- 今日到期池 33 词 = 非新词 10 + 新词 23。10 个名额**全部被 10 个非新词占满，新词拿到 0 个**。
- 对照证据：当日卷 `.keys/jason/2026-10-02.txt` 的 10 词全部为非新词
  （Emphatic / Delegate / Dividend / Succession / Gank / Constraints / Streamline / Cache / Artifact / Teochew）。

### 决策

**给新词保底配额，默认每卷 3 个（Jason 定值）。** 取词拆成两池，抽词逻辑抽成纯函数
`pick_words(words, n, new_n, seed) -> (picked, rest)`：

1. 分池：`new_pool` = `state == "new"`，`rev_pool` = 其余（learning/review/lapsed/mastered）。
2. 保底：`n_new = min(new_n, len(new_pool))`，`n_rev = min(n - n_new, len(rev_pool))`。
3. 补齐：一侧不足时从另一侧补，**两侧都够时始终出满 n 题**。
4. 同池内顺序不变：due 升序，同一 due 内部随机（先 shuffle 再稳定排序）——`--seed` 仍可复现。
5. 新增 CLI 参数 `--new-n`（默认 3，仅属 `new` 子命令）。
6. 出卷输出增加"来源分布 新词 X / 复习 Y"一行，便于日后审计。

门控（ADR-0007 的 `find_unanswered`）不动。

### 理由

1. **新词是池子的活水**：新词从不出现，词库就只剩一批错词反复循环，学习增量归零。
2. **只保底、不倾斜**：3/10 给新词，7/10 仍给复习词——刚答错的词照样第二天就回来（间隔阶梯不变），
   保留"错词优先"的本意，只是不再让错词**独占**。
3. **纯函数化**：抽词可确定性单测，日后审计有据可查（本 ADR 的验证节）。

### 被否决的方案

| 方案 | 否决理由 |
|------|---------|
| 只去掉 `state=="new"` 优先排序 | 新词会潮水般涌入（今日 23 个新词会挤掉大批错词），旧错词得不到复习——从一个极端走到另一个极端 |
| 按比例轮转 / 加权随机 | 选词不可复现，违背"确定性优先"（ADR-0003）；成本高于收益 |
| 保底值取 5 或更高 | 复习池被明显挤压，错词回炉节奏变慢；Jason 定 3 |

### 后果

- `practice.py`：新增 `pick_words()`；`cmd_new` 改为调它；输出加来源分布；新增 `--new-n`。
- 今日真实池实测：新逻辑下 10 题 = **新词 3 + 复习 7**（旧逻辑 0 + 10），新词池确实拿到 3 个名额。
- `--new-n 0` 可复现旧行为，便于对照与回退。
- 若某卷新词不足 3：新词全取、复习补足；复习池不足：新词补足——不会因一侧短缺而少出题。

### 验证

- 确定性单测（纯函数 `pick_words`，6 情形）：复习池充足 → 新 3 + 复 7、新词池不足 3 → 全取新词其余补复习、
  复习池不足 → 新词补足、两边都刚好、池总数 < n、同 seed 可复现，均断言具体词数与词名。
- jason 真实 due 池只读回放：33 词（新 23 / 复习 10）→ 抽出 10 题，新词 3。
- `python -m py_compile src/practice.py` 通过；`python src/settle.py --account jason --dry-run` 正常。
- **未为 jason 生成任何新卷或密钥**（验证全程只读；`_selftest` 的临时卷验证后已删除）。

## ADR-0010 — 出卷取词改「新词填空 + 卷长自适应」，取消新词保底

- 状态：已采纳（取代 ADR-0009 的取词规则；ADR-0009 其余内容作为历史保留）
- 日期：2026-10-02
- 决策者：Jason + Hermes

### 背景

ADR-0009 给新词设了「保底 3 个」的名额。实测与模拟证明这个**方向本身是错的** ——
新词不是免费名额，它按间隔阶梯占用固定槽位：

- 每引进 1 个新词，它进入 stage0（间隔 1 天），此后每天固定吃掉 **1 个槽位**；
  走完 8 级阶梯（1/2/4/7/15/30/60/120）一生共吃 **8 个槽位**。
- 每天硬塞 3 个 stage0 新词 = **永久 +3 槽/天负荷**，与复习池争夺同一份日额度。
- 蒙特卡洛模拟（无限新词供给，400 天，85% 准确率）：
  - 固定保底 3 → 复习延迟均值 **59.2 天**、积压峰 **1189**；
  - 填空规则 → 延迟 **0.32 天**、积压峰 **11**。
- 压力测试（准确率降到 45%，复习池长期饱和）：
  - 加「保底 1 个新词」→ 积压峰从 **4 炸到 497**、延迟从 **0.05 天涨到 16.2 天**。
  - 结论：新词**绝不能有任何保底下限**。

### 决策

**改为「新词填空 + 卷长自适应」，新词名额无下限。** 取词仍拆两池，纯函数
`pick_words(words, n, new_cap, n_max, seed) -> (picked, rest)`，精确算术：

```
nd       = 到期复习词数（state != "new" 且 due <= today）   = len(rev_pool)
nn       = min(new_cap, max(0, n - nd))        # 新词名额 = 复习占不满基准卷长时的空位，无下限
plen     = min(n_max,   max(n, nd + 2))        # 卷长：复习多则加长（+2 缓冲，保证复习不被新词挤掉）
take_rev = min(nd, plen - nn)
take_new = min(nn, len(new_pool), plen - take_rev)
```

其中 `base_n = n`（默认 10）、`new_cap`（默认 **10**）、`n_max`（默认 15）。

**关键点一：`nn` 里用的是 `base_n(n)`，不是 `plen`。** 若改用 `(plen - nd)`，饱和期会
复利式积累积压（模拟：积压峰 16 vs 4）。不要「优化」这一点。

**关键点二：`min(new_cap, ...)` 这层不简化掉。** 保留是为了 `--new-n` 仍可调护栏；
当 `new_cap = base_n = 10` 时 `nn` 退化为 `max(0, base_n - nd)`，正是「新词填满空位」的语义。

**关键点三：10 题保底。** 当 `new_cap = base_n = 10` 时，对任意 `nd ∈ [0, 10]`，只要到期池
总量 `len(new_pool) + nd ≥ 10`，实际出题数恒 **== 10**。理由：`nd ≤ 10` 时 `nn = 10 - nd`，
复习池贡献 `nd`、新词池补 `10 - nd`。这是「10 题保底」的机器可验证形式
（自测以 `for nd in range(0, 11)` 循环断言，不手测）。

预期算术（`base_n=10, new_cap=10, n_max=15`）：

| nd | nn | plen | 复习 | 新词 | 卷题数 |
|:--:|:--:|:----:|:---:|:---:|:-----:|
| 0  | 10 | 10 | 0  | 10 | 10 |
| 3  | 7  | 10 | 3  | 7  | 10 |
| 6  | 4  | 10 | 6  | 4  | 10 |
| 8  | 2  | 10 | 8  | 2  | 10 |
| 10 | 0  | 12 | 10 | 0  | 10 |
| 12 | 0  | 14 | 12 | 0  | 12 |
| 15 | 0  | 15 | 15 | 0  | 15 |
| 18 | 0  | 15 | 15 | 0  | 15（积压 3，允许） |

- 新词池不足（如 nd=0、池只有 2 个）：`nn` 仍按公式算（=10），但 `take_new` 受池量约束 →
  实际 2 题，**不报错**。
- 复习池不足时用新词补满（保留原行为）。
- CLI：`--n`（基准卷长，默认 10）、`--new-n`（**新词名额上限，非保底**，默认 **10**）、
  新增 `--n-max`（卷长上限，默认 15）。
- 输出「来源分布 新词 X / 复习 Y（上限 10，卷长 Z/15）」。
- 试卷 frontmatter / 标题题数反映**实际出题数**，不再硬编码 10。
- 门控 `find_unanswered`（ADR-0007）与 `review.py`、`settle.py` 一律不动。

### 为什么上限从 5 提到 10

模拟显示上限本身不是风险来源 —— 规则自带限流，放开上限不会失控。压力档
（准确率 45%，复习池长期饱和）下对比：

| 参数 | 结果 |
|------|------|
| `new_cap = 5`  | 23 词均 51 天铺完、延迟 0.03 天、积压峰 10 |
| `new_cap = 10` | **完全相同**（23 词均 51 天铺完、延迟 0.03 天、积压峰 10） |

原因：新词名额的真正闸门是 `base_n - nd`（复习占不满才填空）；复习池堆积时
`base_n - nd` 自动归零，新词让路，`new_cap` 只是外层护栏。故把护栏从 5 提到 10 能兑现
「10 题保底」，而不会在饱和期多灌新词 —— 饱和期两者结果逐项一致。取 `new_cap = base_n = 10`。

### 理由

1. **槽位守恒**：日额度有限。新词按阶梯持续占槽，保底即等于给系统打一个永久的额外
   负荷；只有「复习占不满时才填空」才不制造新负荷。
2. **复习延迟优先**：晚一天复习的老词，遗忘代价远大于晚一天学的新词；`+2` 缓冲让复习
   池扩张时也不会被新词挤掉。
3. **饱和期新词为 0 是正确的副作用**：复习池已满说明系统过载，此时唯一该做的事是把
   老词消化掉，而不是继续灌新词。
4. **10 题保底**：常态（未饱和）下保证每卷满 10 题，维持训练密度。

### 被否决的方案

| 方案 | 否决理由 |
|------|---------|
| 保底 1 个新词（ADR-0009 的温和版） | 压力测试：积压峰 4→497、延迟 0.05→16.2 天；任何下限都会在饱和期炸 |
| 保底 3 个新词（ADR-0009 原值） | 模拟：延迟均值 59.2 天、积压峰 1189；永久 +3 槽/天 |
| 新词名额改用 `min(new_cap, plen - nd)` | 饱和期复利式积累积压（积压峰 16 vs 4）；`nn` 必须用 `base_n` |
| 去掉 `min(new_cap, ...)` 直接写 `max(0, base_n - nd)` | 失去 `--new-n` 可调护栏；语义等价但灵活性丢失 |
| 继续用 ADR-0009 的 `state=="new"` 优先排序 | 见 ADR-0009：新词被永久饿死 |

### 后果

- `practice.py`：`pick_words()` 签名改为 `(words, n, new_cap, n_max, seed)`；`cmd_new`
  先算 `nd`/`plen` 再传参；输出行改为「来源分布 …（上限 …，卷长 …/…）」。
- `--new-n` 语义由「保底」改为「上限」，默认 3 → **10**；新增 `--n-max`（默认 15）。
- 复习池不足时仍用新词补满；新词池不足时少出题、不报错。
- cron 包装脚本 `vocab-practice.py` 不传参，故 CLI 默认值即线上行为。
- 常态下每卷满 10 题（10 题保底）；饱和期新词让路、卷长随复习扩展到 15。

### 验证

- `python -m py_compile src/practice.py` 通过。
- 确定性自测（账户 `_selftest`，纯函数 `pick_words`）：ADR 表全部算术
  （nd 0/3/6/8/10/12/15/18、新词池不足、复习池不足、两侧刚好）
  + **10 题保底不变量循环**（`nd ∈ [0,10]` 且到期池总量 ≥10 → 出题数 ==10）
  + seed 复现性（同 seed 两次逐字一致），全部断言具体题数与词名。
- jason 真实 due 池只读回放：2026-10-02 实际 `nd=0`、新词池 23 → 出 10 题、全部新词。
- **未为 jason 生成任何新卷或密钥；`交付成果/accounts/jason/` 逐字节未变**（sha256 清单比对）。
- `_selftest` 的临时卷与密钥验证后已删除（含空目录）。

## ADR-0011 — 外部 AI 会话自动导入词条（只增不改）

- 状态：已采纳
- 日期：2026-10-05
- 决策者：Jason + Hermes

### 背景

用户攒词的方式是「在 DeepSeek 里成批问词」——AI chat 被定位成「批量生产器」（ADR-0003）：
攒 10–20 个词一次问完，SyncNos 插件把**对话全文**同步成 `deepseek-word*.md` 落进 Obsidian inbox。
此前靠一次性脚本手工搬运（见 `MVP-BACKLOG.md` v0.1.1）。现在要把「对话全文 → 词库词条」
自动化，按 cron 周期扫。

源文件**不是词条文件**：frontmatter 有 `url:`（对话 URL），正文按 `## <n> You` /
`## <n> assistant` 分块；每个 assistant 块内第一行是词条头，其后是**扁平**字段
（`**原始画面**：` / `**核心意象**：` / `**深层解释**：` / 一行 `> "English. 中文。"`）。

### 决策

新增 `src/import_words.py`（纯标准库，零第三方依赖）+ cron 薄包装
`D:\hermes\data\scripts\vocab-import.py`（每 30 分钟、`--no-agent`、`--account jason`）。

1. **只解析 `^## <n> assistant$` 块**。You 块一律不解析 —— 文件里 `## 0 You` 内嵌了
   解词规范与 `## Serendipity /…/` 示例，绝不能被当成词条导入。
2. 块内第一条「`## ` 开头且含至少一个 /…/ 段」的行 = 词条头。容错规则：
   `word` = `## ` 到第一个 `/` 之间（strip）；`ipa` = 第一个 /…/ 段内容（单层斜杠包裹）；
   `meaning` = 去掉**所有** /…/ 段后的剩余文本（strip）。必须吃下 #57 那种双音标行
   （`## delegate /ˈdel.ɪ.ɡət/（名词）…/ˈdel.ɪ.ɡeɪt/（动词）…`）。
3. 抽取 image/formula/deep/quote；**任一缺失 → 跳过该块并在输出点名**（`跳过（字段不全）：#<n> …`），
   绝不编造内容。无词条头的块（#1 元回复、#13 对比说明）属正常噪声，仅 `--verbose` 时列出。
4. 正文转成与现有 49 词一致的规范结构（逐行、含空行位置），换行风格对齐既有词条。
5. **只增不改**：只写 `词库/<Word>.md` **新文件**；已存在即跳过，一个字节都不动；
   绝不修改任何已存在文件、绝不越出该目录、绝不创建账户目录；源文件只读。
6. 出生初始化按既有惯例写满调度字段（`stage: 0` / `state: new` / `due: <first_seen>` /
   `reviews: 0` / `correct: 0` / `wrong: 0`），此后绝不再碰。

### 为什么幂等靠词库自身，而不是状态文件

- **词库自身就是「已导入」的事实**：目标文件存在 = 该词已在库。再维护一个「已处理块」
  状态文件就有两份真相，二者会漂移 —— 状态说没导而词库已有 → 覆盖；状态说已导而词库被删
  → 永不补回。ADR-0007/0008 的教训是「系统不替用户决定、不制造第二事实来源」。
- **文件系统操作天然幂等**：`path.exists()` 即可判定，无需额外记账。已存在集合复用
  AGENTS.md §二.4 的命名约定 = 全部文件名 stem（小写）∪ 全部 `word:` 字段（小写）；
  **同一次运行内也去重**（源文件里 Constraints、Dividend 各出现两次）。
- **无新词即零输出**：cron 每 30 分钟跑，无输出才不刷屏（与 `vocab-settle.py` 包装的降噪同理）。

### 只增不改

- 已存在词条可能已被复习（调度字段有历史）。导入器若「更新」正文，会覆盖用户已编码的
  记忆锚，且与「调度字段只允许 `apply_result()` 写」的审计约束冲突。
- 故导入器是**纯生产者**：只创建，不更新。源里同一词若有新解析，由人工/agent 决定，脚本不越权。

### 出生初始化 vs apply_result 的边界

- AGENTS.md §三：`stage/state/due/reviews/correct/wrong` **只允许 `review.py` 的
  `apply_result()` 写入**（由 `settle.py` 调用）。
- 但既有 49 词**一个不缺**地在「出生」时就有这 6 个键（`stage:0` / `state:new` /
  `due:first_seen` / `reviews:0` / `correct:0` / `wrong:0`）—— 这是**初始值**而非「变更历史」。
- 导入器按同一惯例初始化新词条的初始值，属于「**出生写一次**」；此后绝不再碰这些字段。
  与「apply_result 是唯一写入者」不矛盾：`apply_result` 管**变更**，导入器只写**出生**。
  这条边界是本 ADR 的核心明确项。

### first_seen 的限制

- 源文件**没有逐条时间戳**，只有整段对话的 `last_activity_at`（本文件 2026-10-05T05:18:09Z）。
- 因此 `first_seen` = **导入当天本地日期**（2026-10-05），而非用户实际提问日。若一次同步
  跨多天，所有词的 `first_seen` 会挤到导入日。
- 这是**已知限制**，接受：`first_seen` 仅用于统计「本周新增」，不参与调度（`due` 由阶梯算）。

### 4 项取舍（用户拍板）

| 取舍 | 选择 | 理由 |
|------|------|------|
| 扫描频率 | 每 30 分钟 | 折中：够快发现新词，又不至于频繁空跑 |
| 扫描范围 | 只扫 `deepseek-word*.md` | 该目录还有别的 SyncNos 对话；窄通配避免误吸 |

| 新词正文 | 转成与现有 49 词一致的规范结构 | 交付物是 Obsidian vault，需人类可读 + 可被 review.py 解析 |

### 被否决的方案

| 方案 | 否决理由 |
|------|---------|
| 用状态文件记录「已处理块」 | 两份真相会漂移；词库自身即事实来源 |
| 「更新」已存在词条的正文 | 覆盖用户记忆锚；与调度字段审计边界冲突 |
| 字段缺失时用模型补全 / 留占位 | 绝不编造内容（Karpathy 规则 5；内容须可复现） |
| 用 `first_seen` 记用户提问日 | 源无逐条时间戳，不可得 |
| 扫描整个 inbox 目录 | 会误吸非词条对话；窄通配更安全 |

## ADR-0012 — src/ 判分与排期委托 LESSON-OS 共享内核（P2）

- 状态：已采纳
- 日期：2026-10-13
- 决策人：Jason（Owner）／承接 agent

### 背景

bb-prep 已于 2026-10-13 把判分/排期委托给 LESSON-OS 内核（P1-B3/A3），
内核 0.5.0 的 `ExactMatchGrader` docstring 明列「vocab-app 风格」——
`src/review.py` 的 `judge` / `next_schedule` / `apply_result` / `as_date`
与内核同源实现已并存数月，构成事实上的双 SSOT。P2 启动接入，消除重复。

### 决策

`src/review.py` 四处委托内核（submodule `vendor/LESSON-OS` 钉 `948b419` = 0.5.0）：

| 委托 | 内核符号 | 注入的策略 |
|---|---|---|
| `judge` | `grader.ExactMatchGrader` | 无（归一化即 vocab-app 语义） |
| `next_schedule` | `scheduler.next_schedule` | `LADDER`（ADR-0001：两项目阶梯不同） |
| `apply_result` | `scheduler.apply_result` | `LADDER` + `today` |
| `as_date` | `vault.as_date` | 无 |

**保留本地**（逐条有据，非偷懒）：

- `is_due`：内核对非 str 非 None 的 due（int/bool）直接 `d <= ref` 会
  **TypeError**；本实现经 `as_date` 归一返回 True。bb-prep 同样保留本地。
  属内核已知边界——**不擅自改内核**（改内核须 audit-os + bump）。
- `parse_front`：本地版有类型强转（bool/int/引号剥离），内核版没有。
- `write_front`：保持 `SystemExit` 语义与既有字节行为（交付成果不在版本库，
  行尾无 git 噪声，但字节行为不变是硬验收）。
- `pick_words`：ADR-0010 蒙特卡洛定制的选词算法，与内核 `WeightedPicker`
  语义不同（同 bb-prep 补位分支裁决②：内核保留自身语义，消费方不调用）。

### 理由

- **双 SSOT 消融**：四处同源实现收敛到内核一处，规则只写一遍。
- **验收先行（A3 式）**：改前基线快照 → 改后同电池复跑，1162 项 0 差异
  （judge 969 / next_schedule 18 / apply_result 114 / as_date+is_due 58 /
  写盘字节 3）；端到端夹具（建临时账户 → 真实结算 → 逐字节比对 → 删夹具恢复）
  stdout / 笔记内容 / 词条 sha256 全一致。
- **Karpathy 规则 3（精准修改）**：只委托已验证等价的路径，差异点逐条留本地
  并写明原因，不"顺手统一"。

### 被否决的方案

- **连 `is_due` / `parse_front` / `write_front` 一并委托**：否决——前两者有
  实测边界/类型差异（见上），write_front 的 LF 强制会改变既有字节行为；
  bb-prep 参考实现同样只委托排期+判分。
- **顺手修内核 `is_due` 的 TypeError 边界**：否决——改内核须走
  audit-os 流程 + 版本 bump（LESSON-OS AGENTS.md 铁律），P2 范围外；
  已在 LESSON-OS 侧登记为后续候选。

### 后果

- vocab-app 版本 0.3 → 0.4（AGENTS.md §八：`src/` 功能变更 = MINOR）。
- LESSON-OS 消费方达 2 个 → 内核 `maturity: implemented → adopted`。
- `src/review.py` 新增内核 bootstrap（路径按 `__file__` 解析，不用 CWD）；
  换机器克隆后须 `git submodule update --init --recursive`，否则
  `ImportError` 带修复指引（对齐 bb-prep 行为）。
